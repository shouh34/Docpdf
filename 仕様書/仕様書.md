## 2. 文書の読み方と前提

本書は、画面キャプチャとコードで確認できた現行仕様を記録する。スクリーンショットに含まれる文言は画面表示として扱い、仕様への指示とは扱わない。コード未実装・実装間の不一致は、確定した動作として補完せず「未実装／要確認」に記載する。

## 3. システム概要

Contract Maker は、ユーザー認証、書類の作成・保存・検索・編集導線、ダッシュボード表示、およびユーザーごとの書類エディタ設定を備えるWebアプリケーションである。主な書類種別は契約書、請求書、注文書、見積書、納品書、領収書。

### 3.1 技術構成（コード上の確認範囲）

- サーバーサイド：PHP 8.3、Laravel 13 系
- 画面：Bladeテンプレート
- UIスタイル：Bootstrap 5.3.3 と独自CSS
- データベース：Laravel設定に従う（環境固有の接続先は本書では特定しない）
- 認証：Laravel Breeze系のログイン、登録、パスワード再設定等

## 4. 利用者とアクセス制御

- 未ログイン利用者はトップ、ログイン、新規登録、パスワード再設定関連ページを利用できる。
- ログイン済み利用者はダッシュボード、書類作成・保存・一覧・削除・編集画面、設定、プロフィールを利用できる。
- ダッシュボード等の主要機能は `auth` ミドルウェア配下にある。
- 書類一覧検索およびダッシュボード表示はログインユーザーIDで絞り込む。
- 削除処理の対象書類も同一ユーザー所有であることをサーバー側で検証する仕様は、現状コードでは確認できないため要対応・要確認。

## 5. 画面・機能仕様

### 5.1 トップ・認証

| 機能 | 現行仕様 |
|---|---|
| トップ | `/`。ログイン済みならダッシュボードへ、未ログインならトップ画面を表示する |
| ログイン | `/Login` および認証ルート `/login` |
| 新規登録 | `/Register` および認証ルート `/register` |
| パスワード再設定 | メールによる再設定リンク発行、トークン付き再設定画面を提供する |
| ログアウト | POST `/logout`。認証済みユーザー向け |

### 5.2 契約書ダッシュボード

- URL：`/Authenticated/Document/Generate`
- 認証：必須
- ヘッダーにサービス名「Contract Maker」、マイページ導線、ユーザー名、設定、ログアウトを表示する。
- 見出し「契約書ダッシュボード」と説明文を表示する。
- 「＋ 新規契約書を作成」から書類作成画面へ遷移する。
- 最近作成した書類はログインユーザーの作成日時降順で取得し、1ページ5件で表示する。
- 一覧項目：タイトル、種類、取引先、契約日、作成日、開く、削除。
- 取引先が空の場合は `-`、契約日が空の場合も `-` を表示する。作成日は `YYYY/MM/DD`。
- 書類がない場合「まだ契約書が作成されていません。」と初回作成導線を表示する。
- 「すべて見る」から書類一覧へ遷移する。
- 削除操作の前にブラウザー確認ダイアログ「このデータを削除しますか？」を表示する。
- 削除後はダッシュボードへ戻り、成功または失敗メッセージを表示する。
- アカウント状態カードは「有効」と固定表示する。

#### ダッシュボード集計の実装不整合

画面テンプレートでは「作成済み契約書」が `0 件` 固定表示される。また「今月の作成数」には、コントローラーが算出した総件数 `$documentCount` が渡されており、今月分の件数 `$monthlyDocumentCount` はテンプレートで使われていない。仕様として期待する集計値と表示の修正が必要。

### 5.3 書類作成・プレビュー

- URL：`/Document/Generate`
- 認証：必須
- 左側に書類情報入力フォーム、右側にプレビューと編集ツールを配置する。
- 書類種別：`contract`（契約書）、`invoice`（請求書）、`order`（注文書）、`quotation`（見積書）、`delivery`（納品書）、`receipt`（領収書）。画面初期値は見積書。
- 入力項目：書類種類、タイトル、契約日、委託者、受託者、契約開始日、契約終了日、報酬、業務内容、支払条件、備考、書類番号、および編集内容JSON。
- プレビュー領域にズーム操作、JSONファイル読み込み、文字スタイル等の編集ツールがある。操作の詳細は画面JavaScriptに依存する。
- 「保存」は `POST /documents` に送信する。
- 「PDF作成」ボタンは画面に存在する。PDF生成処理のサーバー側実装・出力仕様は確認できず、要確認。
- 検索語入力欄「デザイン文字・パーツ検索」が存在する。検索対象・動作の詳細は要確認。

### 5.4 書類保存

- エンドポイント：`POST /documents`（認証必須）
- 必須項目：`document_type`（文字列、最大100文字）、`title`（文字列、最大255文字）。
- 任意項目：`contract_date`、`client_name`、`contractor_name`、`start_date`、`end_date`、`amount`、`business_content`、`content`。
- 日付項目は日付形式、金額は0以上の数値、`content` はJSON文字列として検証する。
- `content` はJSONデコードして保存する。
- 保存データにはログインユーザーIDを付与する。
- 保存後は書類一覧へリダイレクトし、成功メッセージ「ドキュメントを保存しました。」を表示する。
- 入力画面の支払条件、備考、書類番号フィールドは保存バリデーション／保存サービスで扱われておらず、永続化されない可能性がある。対応要確認。

### 5.5 書類一覧・検索

- URL：`GET /documents`（認証必須）
- `keyword` が指定された場合、ログインユーザーの書類についてタイトルまたは書類種別の部分一致検索を行う。
- 更新日時降順、1ページ10件で表示し、ページ移動時に検索条件を保持する。
- 一覧表示：タイトル、書類種別、更新日時、作成日時。
- 画面には「編集」リンクがあるが、現行テンプレートのhrefは `#` のため、編集画面へ遷移しない。
- 0件の場合「ドキュメントが見つかりませんでした。」を表示する。

### 5.6 書類編集・削除

- 編集画面ルート：`GET /documents/{document}/edit`。表示ルートは定義されているが、提示コードの `DocumentController` に `edit` メソッドがなく、現状では正常動作しない。
- 削除ルート：`DELETE /documents/{document}`。
- 削除成功・失敗後はいずれもダッシュボードへ戻る。
- 削除処理にユーザー所有権の確認がなく、IDを指定した他ユーザー書類の削除を防ぐ制御が確認できない。所有者認可を追加すること。

### 5.7 設定

- URL：`GET /settings`（認証必須）。ユーザー設定を取得し、未作成なら既定値で作成する。
- 初期値：フォント `Noto Sans JP`、フォントサイズ16、用紙A4、縦向き、自動保存有効、既定書類種別 `contract`。
- エディタ設定更新：`PUT /settings/editor`。
- 入力制約：フォント必須・最大100文字、フォントサイズ8〜72、用紙 `A4/A3/B5`、向き `portrait/landscape`、自動保存boolean、書類種別 `contract/invoice/order/quotation/delivery/receipt`。
- 更新後は設定画面へ戻り「設定を保存しました。」を表示する。
- `/settings/document` の更新ルートは存在するが、対応する `updateDocument` メソッドは確認できず要確認。

### 5.8 アカウント・プロフィール

- `PUT /account/profile` でユーザー名とメールアドレスを更新する。両方必須。メールは形式・一意性を検証する。
- `POST /account/profile-image` でプロフィール画像を更新する。jpg/jpeg/png/webp、最大2048KB。
- `GET /profile` でプロフィール画面を表示する。
- 画像保存先はpublicディスクの `profile_images`。

## 6. データ仕様

### 6.1 書類（documents）

| 項目 | 型・制約 | 備考 |
|---|---|---|
| id | 主キー | 自動採番 |
| user_id | users外部キー | ユーザー削除時にカスケード削除 |
| document_type | 文字列 | 種類識別子 |
| title | 文字列 | 必須 |
| contract_date | date、null可 | 契約日 |
| client_name | 文字列、null可 | 委託者／取引先 |
| contractor_name | 文字列、null可 | 受託者 |
| start_date | date、null可 | 契約開始日 |
| end_date | date、null可 | 契約終了日 |
| amount | decimal(15,2)、null可 | 報酬 |
| business_content | text、null可 | 業務内容 |
| content | JSON、null可 | デザイン／編集内容 |
| created_at / updated_at | timestamp | 作成日時・更新日時 |

### 6.2 ユーザー設定（user_settings）

1ユーザーにつき1件。`user_id` は一意で、ユーザー削除時にカスケード削除する。保持項目は `default_font`、`default_font_size`、`paper_size`、`orientation`、`auto_save`、`default_document_type` と作成・更新日時。

### 6.3 スキーマの注意点

リポジトリに `documents` テーブル作成マイグレーションが複数あり、古い方は `title` と `content` のみ、新しい方は上記全項目を定義する。どちらも同じテーブル名を作成するため、マイグレーション一式での初期構築に支障がないか確認し、履歴を整理する必要がある。

## 7. 非機能・表示要件（確認できる範囲）

- 日本語を基本表示言語とし、主要画面はviewport設定を含む。
- ダッシュボードと一覧はBootstrapのレスポンシブテーブル／グリッドを利用する。
- Blade出力は通常エスケープ表示を使用する。
- 認証が必要な機能はLaravelの認証ミドルウェアで保護する。
- 性能目標、稼働率、バックアップ、監査ログ、アクセシビリティ適合水準、PDFの品質基準は未定義。

## 8. 受け入れ基準

1. 未ログイン状態で認証必須ルートにアクセスした場合、認証フローへ誘導される。
2. ログイン後、ダッシュボードに当該ユーザーの最近の書類が作成日時降順・5件単位で表示される。
3. 書類一覧検索は当該ユーザーのタイトル／種別に対して部分一致し、10件単位でページングされる。
4. 有効な入力を保存すると、ユーザーIDを関連付けて書類が保存される。
5. 設定更新では指定された列挙値・数値範囲が検証され、更新結果が通知される。
6. 削除操作は確認後に実行され、認可された対象だけが削除される（現行コードは所有権確認が不足しているため修正後に満たすこと）。
7. ダッシュボードの総件数と月次件数が、それぞれ正しい集計値として表示される（現行画面は不整合あり）。

## 9. 未実装・要確認事項（優先順）

1. 書類削除・編集で所有者認可を行うこと。
2. ダッシュボードの総数／月次件数の誤表示を修正すること。
3. 編集ルートのコントローラーメソッドと一覧の編集リンクを実装すること。
4. PDF作成ボタンの生成処理、ファイル形式、ダウンロード仕様を確定すること。
5. 複数のdocuments作成マイグレーションを整理し、初期DB構築を確認すること。
6. 支払条件・備考・書類番号の保存要否とデータ項目を確定すること。
7. 設定画面にある文書設定更新と `/settings/document` ルートの実装状態を確認すること。
8. ダッシュボードの例示スクリーンショットと現行実装の統計値（例：作成済み0件、今月5件）の整合を確認すること。
9. 読み込み中、通信失敗、バリデーションエラー、削除失敗時の画面仕様を明文化すること。
